# LoggedInUser Component - Usage Notes

## Overview

`LoggedInUser` displays information about the currently authenticated user in the application header or another user-account area.

The component provides:

* User avatar
* Automatic initials when an image is unavailable
* Consistent avatar colors based on the user's name
* First/last name formatting through the reusable `UserName` component
* User role
* Expandable account menu
* Email address
* Last session information
* Notification toggle
* Profile
* Account settings
* Login as another user
* Logout
* Outside-click and Escape-key menu closing

The component is designed to work with the project's slug-driven component loader.

# data.json

All user-specific configuration for the component is stored in `data.json`.

Example:

```json
{
  "user": {
    "id": "user-001",
    "name": "Shankar Krishnasamy",
    "role": "UI Designer",
    "email": "shankar@example.com",
    "image": "/img/users/PawelKuna.jpg",
    "status": "online",
    "lastSession": {
      "start": "2026-08-25T08:10:00",
      "end": "2026-08-25T16:30:00"
    }
  },
  "notifications": {
    "enabled": true
  },
  "menu": {
    "profile": true,
    "settings": true,
    "notifications": true,
    "switchUser": true,
    "logout": true
  }
}
```

# User Properties

## id

Unique identifier for the user.

Example:

```json
"id": "user-001"
```

This can later be connected to the application's authentication system.

---

## name

Full user name.

Example:

```json
"name": "Shankar Krishnasamy"
```

The name is passed to the reusable `UserName` component.

The `UserName` component handles:

* First name
* Last name
* Last-name styling
* Two-line display for longer names

The component can therefore handle names such as:

```text
Pawel Kuna
Shankar Krishnasamy
Mary Jane Watson
```

---

## role

The user's role.

Example:

```json
"role": "UI Designer"
```

The role is displayed below the user's name in a muted style.

---

## email

The email address associated with the current login.

Example:

```json
"email": "shankar@example.com"
```

The email is displayed in the account dropdown.

This is useful because it tells the user exactly which account they are currently logged in as.

---

## image

Path to the user's avatar image.

Example:

```json
"image": "/img/users/PawelKuna.jpg"
```

Images for users are stored in:

```text
public/img/users/
```

Because files in `public` are served from the site root, the JSON path should start with:

```text
/img/users/
```

Example:

```json
"image": "/img/users/PawelKuna.jpg"
```

# Avatar Fallback

If:

* `user.image` is empty, or
* the image fails to load

the component automatically displays the user's initials instead.

For example:

```text
Shankar Krishnasamy
```

becomes:

```text
SK
```

The initials are generated by:

```js
getInitials(user.name)
```

The avatar background color is generated by:

```js
getAvatarColor(user.name)
```

The color is deterministic, meaning the same name always produces the same avatar color.

The color palette contains muted colors deliberately so that automatically generated avatars avoid highly saturated colors.

These functions are located in:

```text
src/utils/user/userUtils.js
```

---

# Last Session

The last session is stored as start and end timestamps.

Example:

```json
"lastSession": {
  "start": "2026-08-25T08:10:00",
  "end": "2026-08-25T16:30:00"
}
```

The component does not store a formatted duration such as:

```text
8h 20m
```

The duration is calculated automatically.

This avoids having duplicated or stale information in the JSON.

The session formatting utilities are located in:

```text
src/utils/user/sessionUtils.js
```

The utilities handle:

* Relative session date
* Session start/end time
* Session duration

Examples of relative dates:

```text
Today
Yesterday
3 days ago
2 weeks ago
2 months ago
1 year ago
```

The session display is intentionally compact:

```text
Last session - 6d ago
Aug 25 · 8:10 AM – 4:30 PM
8h 20m
```

The relative date provides context while the actual session date/time provides precise information.

# Notifications

Notification state is controlled through:

```json
"notifications": {
  "enabled": true
}
```

The notification menu item is a single clickable row.

The user can click anywhere on the notification row:

```text
Bell + Notification + empty space + switch
```

to toggle notifications.

The visual switch is not a separate button. This avoids placing a button inside another button.

The component uses:

```jsx
role="menuitemcheckbox"
```

and:

```jsx
aria-checked={notificationsEnabled}
```

to communicate the notification state to assistive technologies.

# Menu Configuration

The menu is controlled by the `menu` object.

Example:

```json
"menu": {
  "profile": true,
  "settings": true,
  "notifications": true,
  "switchUser": true,
  "logout": true
}
```

Each option can be enabled or disabled independently.

## profile

```json
"profile": true
```

Displays:

```text
Profile
```

---

## settings

```json
"settings": true
```

Displays:

```text
Account settings
```

---

## notifications

```json
"notifications": true
```

Displays:

```text
Notification    [switch]
```

---

## switchUser

```json
"switchUser": true
```

Displays:

```text
Login as another user
```

This is useful when the application supports switching between accounts.

---

## logout

```json
"logout": true
```

Displays:

```text
Logout
```

Login-as-another-user and Logout are grouped together at the bottom of the menu.

---

# Menu Behaviour

The account dropdown opens when the user clicks the main user button.

It closes when:

* The user clicks outside the component
* The user presses `Escape`
* A menu action such as Profile, Account settings, Login as another user, or Logout is clicked

The Notification option is different.

Clicking Notification intentionally keeps the menu open because it is a setting rather than a navigation action.

# Slug-Driven Component Loader

`LoggedInUser` does not need its own page or route.

It is registered through the project's component configuration.

The component can therefore be loaded by the existing slug-driven component loader.

The component is exported through:

```text
src/components/UI/index.js
```

For example:

```js
export { default as LoggedInUser } from "./Users/LoggedInUser/LoggedInUser";
```

The corresponding entry should exist in:

```text
src/data/components.json
```

and the navigation entry should be added to:

```text
src/data/componentNavigation.json
```

The exact slug should follow the project's existing component naming conventions.

## sessionUtils.js

Location:

```text
src/utils/user/sessionUtils.js
```

Responsible for session-related formatting such as:

```js
formatSessionRelativeDate()
formatSessionTime()
formatSessionDuration()
```

This keeps `LoggedInUser.jsx` focused on rendering and interaction rather than date calculations.

---

# Important Code Cleanup

`LoggedInUser.jsx` should import the session formatting functions from `sessionUtils.js`.

For example:

```js
import {
  formatSessionRelativeDate,
  formatSessionTime,
  formatSessionDuration,
} from "@/utils/user/sessionUtils";
```

Do not also define `formatSessionDuration()` inside `LoggedInUser.jsx`.

There should be only one implementation in:

```text
src/utils/user/sessionUtils.js
```

This prevents duplicate logic and makes the utility reusable by the future `GuestUser` component.

# Future GuestUser Component

A separate `GuestUser` component is planned for users who are not currently logged in.

It should follow the same general visual style as `LoggedInUser`.

Suggested structure:

```text
src/components/UI/Users/
├── LoggedInUser/
├── GuestUser/
└── UserName/
```

`GuestUser` can use local storage to remember the previous session on the current machine.

If a previous email is available, it can display:

```text
Last session
6d ago · Aug 25 · 8:10 AM
```

and offer:

```text
Login as
shankar@example.com
```

along with:

```text
Login as another user
```

If no previous account is known, it should simply display:

```text
Login
```

The remembered email must only be used as a convenience for pre-filling or suggesting a login. It must never be treated as authentication.

# Design Principles

The `LoggedInUser` component should remain:

* Data-driven
* Reusable
* Independent of a specific page
* Compatible with light and dark themes
* Responsive
* Accessible
* Suitable for long user names
* Safe when an avatar image is missing or fails to load

User data belongs in `data.json`.

User formatting logic belongs in `userUtils.js`.

Session formatting logic belongs in `sessionUtils.js`.

Visual styling belongs in:

```text
LoggedInUser.module.css
```

The component itself should primarily handle:

* State
* User interaction
* Menu visibility
* Notification state
* Rendering
